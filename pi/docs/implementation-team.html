Implementation Team

The implementation-team extension turns Pi into a Chief who coordinates a small implementation team. The Chief does not inspect or change the repository itself. It sends a complete task and a stable issue ID to the team, then reports the reviewer-approved result or a real blocker.

Start it explicitly

Run Pi from the project you want to work in:

pi -e ~/.pi/agent/extensions/implementation-team.ts

The extension intentionally activates only when passed with -e (or --extension). Starting ordinary Pi leaves it inactive.

Workflows

The default workflow file is ~/.pi/agent/agents/implementation-team.yaml. It defines:

  • implementation: planner, then builder, then an independent reviewer.
  • implementation-repair: builder repair, then an independent reviewer.

A project can replace the whole workflow definition with .pi/agents/implementation-team.yaml, relative to that project's root. Use this when a project needs different stages or prompts.

Configure a team in YAML

A workflow is a named sequence of steps. The workflow name is the top-level YAML key. Each workflow has a human-readable description and a steps list. Every step needs an agent name and a prompt. Steps always run in listed order.

frontend-change:
  description: "Plan, build, and review a frontend change"
  steps:
    - agent: planner
      prompt: "Plan the task. Requirements:\n\n$ORIGINAL"
    - agent: builder
      prompt: "Implement the task using this plan. Requirements:\n\n$ORIGINAL\n\nPlan:\n\n$INPUT"
    - agent: reviewer
      prompt: "Review the working tree. Requirements:\n\n$ORIGINAL\n\nBuilder report:\n\n$INPUT"

The YAML reader expects this simple shape: top-level workflow names, an indented description, steps, and list items with agent and prompt. Keep each prompt as one quoted YAML value; use \n inside a double-quoted prompt for line breaks.

Tailor or create a new team

  1. Create .pi/agents/implementation-team.yaml in the project.
  2. Copy the default workflows you still need, then adjust prompts, reorder steps, or add a named workflow such as frontend-change.
  3. Use agent names that Pi can load. The global team includes planner, builder, and reviewer; project agent files may also live in agents/, .claude/agents/, or .pi/agents/.
  4. Tell the Chief which named workflow to use when making the request.

The project YAML replaces the global file; it does not add to it. Put every workflow that project should offer in the override file. A new workflow is a new team arrangement, not a new executable. If you need a new role, add an agent persona file with a matching name, then reference that name in a step.

Prompt variables

  • $ORIGINAL is the complete task passed to the workflow. It stays the same for every step.
  • $INPUT is the prior step's output. For the first step, it is the original task.

Use $ORIGINAL when a stage must retain the full requirements. Use $INPUT to hand a plan, implementation report, or review findings to the next stage. The example above gives the builder both.

Task + issue ID→ Planner→ Builder→ Reviewer→ Approved, or repair

Use it

Tell the Chief what to implement and include a stable issue identifier. The Chief delegates through its run_implementation tool. For a new change it uses implementation; if review requests changes, it uses implementation-repair with the original requirements and review findings.

Watch and inspect the run

While a workflow runs, the dashboard below the editor shows the workflow and issue ID. Each stage shows whether it is pending, running, done, or failed, plus elapsed time, tool-call count, and its latest output line. It is progress information, not a final review decision.

Use /implementation-output to pick a stage and open its live or saved output. To open a known stage directly, pass its agent name:

/implementation-output builder

Agent transcripts and saved stage output are kept under Pi's session storage, separated by project and the supplied issue ID. This lets work on one issue keep its own specialist history without needing to know the exact generated directory name.

Do not run /reload while a workflow is running. Reload shuts down the extension runtime and terminates its active child process. Wait until the workflow finishes or fails before reloading.
